# Strategic Signal Scanner 技术研究与选题流水线

AI 造物社区关注 AI、智能硬件、机器人和人机交互。我在带项目、准备分享和编辑社区内容时，需要持续接触论文、开发工具、产品案例以及新的使用需求。这些材料散落在不同网站和信息源里，有些重复出现，有些标题很吸引人，却很难判断对正在做项目的人究竟有什么用。我因此搭建了 Strategic Signal Scanner，把收集和初步整理变成一套可以重复执行的流程。

我希望它先帮我回答：这条材料来自哪里，是否已经看过，有什么值得进一步研究的变化。流水线从 HTTP/JSON 接口、RSS/Atom 和选定网页采集材料，统一标题、来源、日期和链接，再通过规范化 URL、标题与内容哈希去重。模型负责相关性判断、摘要和研究提示，代码负责保留原始元数据、规范化响应和整理 JSON 输出。这样，我在审核候选时仍能回到来源，而不是只面对一段脱离出处的模型总结。

这类研究任务需要反复执行，但每轮都有明确的结束点。我采用 Cloud Scheduler 调用 Cloud Run Jobs，让容器依次完成采集、评分与 JSON 持久化。Cloud Build 和 Artifact Registry 提供构建和镜像交付路径；Cloud Storage 保存跨轮次需要的状态和历史，避免容器结束后丢失去重记录，也方便回看某条研究候选如何成为候选。

Google 模型接入使用 Google Gen AI SDK，支持 Gemini 的 Vertex 路径，并配置项目、区域、模型和瞬时错误重试。Cloud Run 的运行服务账号通过 ADC 获取凭据，模型访问和存储访问可以放在同一套 Google Cloud 身份与权限设计下。DeepSeek 等接口也保留为可配置适配器，采集、去重、存储和 JSON 输出不必随模型更换而重做。

随着流程展开，数据的去向也需要明确。研究原始材料、评分 JSON 和去重状态放在私有存储中；来源 URL、摘要和评分保留为 JSON，交给后续人工审核；公开代码不包含报告页面、日期归档或公共导出。公开代码保留完整采集、去重、评分与 JSON 输出链路。

Scanner 的输出进入我的编辑工作。我审核来源、挑选与社区有关的变化，再把它们写成 Signal Scanner 的文章、阅读链接或后续讨论。哪些内容值得发布、怎样讲给女性、青少年和跨学科创作者听，仍然需要结合具体项目与读者来判断。发布平台承接后面的内容交付；这两个项目分别解决研究准备和内容服务的问题。

我也在 6 月 25 日的 GDG Community Talk 分享过这套工作流。它可以展开讨论的地方，是怎样把一次模型调用做成有来源记录、跨运行状态和人工判断的持续流程。对研究简报、开发者资源监测等相似任务，这些工程选择同样适用。实现与复现方式见 [Google Cloud 工程案例](GOOGLE_CLOUD_CASE_STUDY.md)与[技术指南](TECHNICAL_GUIDE.md)。
